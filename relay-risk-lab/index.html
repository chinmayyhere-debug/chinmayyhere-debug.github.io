All data is synthetic. To run this in Colab, upload relay-risk-lab-step1.zip and run the cells in order.

2. Finding: bust-outs drain before returns come back

For each bust-out case: hours between the last outflow and the first return (bounced check or ACH return).

In [8]:
gaps = sql("""
WITH drains AS (
  SELECT l.case_id, MAX(t.ts) AS last_drain
  FROM transactions t JOIN transaction_labels l USING (txn_id)
  WHERE l.pattern_tag = 'drain'
  GROUP BY 1
),
first_return AS (
  SELECT l.case_id, MIN(r.returned_at) AS first_return
  FROM returns r JOIN transaction_labels l USING (txn_id)
  WHERE l.pattern_tag = 'bad_deposit'
  GROUP BY 1
)
SELECT case_id,
       (JULIANDAY(first_return) - JULIANDAY(last_drain)) * 24 AS hours_gap
FROM drains JOIN first_return USING (case_id)
""")

case_id = "case_00007"
ev = sql(f"""
SELECT t.ts, t.amount, l.pattern_tag, r.returned_at
FROM transactions t
JOIN transaction_labels l USING (txn_id)
LEFT JOIN returns r USING (txn_id)
WHERE l.case_id = '{case_id}'
""")
ev["ts"] = pd.to_datetime(ev.ts)
ev["returned_at"] = pd.to_datetime(ev.returned_at)

out = ev[ev.pattern_tag == "drain"]

3. Finding: mules take money from many new senders, fast

Total sender count didn't separate mules from legit accounts (a landscaper can have 40 clients). New senders per 30 days did.

Note: this uses the whole six months at once, which is fine for exploring. A live rule would need a rolling window using only past data (step 2).

In [11]:
vel = sql("""
WITH first_seen AS (
  SELECT account_id, counterparty_id, MIN(ts) AS first_ts
  FROM transactions
  WHERE direction = 'in' AND counterparty_id NOT LIKE 'proc_%'
  GROUP BY 1, 2
),
active AS (
  SELECT account_id, JULIANDAY(MAX(ts)) - JULIANDAY(MIN(ts)) + 1 AS active_days
  FROM transactions
  GROUP BY 1
)
SELECT f.account_id,
       COALESCE(al.fraud_typology, 'legit') AS label,
       COUNT(*) * 30.0 / MAX(a.active_days, 14) AS new_senders_30d
FROM first_seen f
JOIN active a USING (account_id)
JOIN applications ap USING (account_id)
JOIN application_labels al USING (application_id)
WHERE al.is_fraud = 0 OR al.fraud_typology = 'shell_mule'
GROUP BY f.account_id
""")

vel.groupby("label").new_senders_30d.describe().round(1)

4. Finding: OCR mismatch on checks is noisy on its own

Mismatch = the amount read from the check image differs from the amount the customer typed.

Notes

Things I got wrong along the way

  • My first mule check compared total sender counts and failed. Switched to new senders per 30 days.
  • Some bust-out outflows were generated before their deposit. Tests only checked the average gap at first, so I added a check that no outflow comes before its first bad deposit.
  • Mule accounts were about 75% of all dollars at risk, which would bias the backtest. Scaled them down and split loss by whose money it is.

Limitations

  • All numbers are made up to be plausible, not calibrated to a real portfolio.
  • Every application was approved, so onboarding outcomes are visible. In real life you never see outcomes for declined applicants.
  • Balances aren't tracked, only flows.
